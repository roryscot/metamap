# Protected activation

P10 connects the P09 approval contract to both existing activation interfaces.
The shared evaluator recompiles the exact captured candidate, verifies its
complete generated byte inventory, and checks approval against the host's current
trust, active baseline and clock. A failed governed request never invokes legacy
promotion. Production installation, credentials and consumer activation remain
separate owner decisions.

## Portable in-memory host

Construct MetamapActivator with the existing relation/constraint registries and
a third host argument. The host selects mode "governed", supplies a configuration
callback and optionally a trusted clock callback. A caller submits one
GovernedActivationRequest containing schemaVersion 1.0.0, proposal, approval and
the complete generated files. It cannot submit trust or a clock in that record.

The request overload of activate returns activated, already-active or rejected.
One assignment publishes the deeply frozen manifest/files state, exposed through
governedCurrent. The legacy current getter and graph/policy overload retain their
legacy types. A governed instance rejects that legacy overload even for a viable
v1 candidate. An ordinary legacy instance cannot opt itself into governance from
an incoming request.

The configuration callback is read again on every request. An exact retry of the
same proposal, approval and files performs no activation and retains the same
manifest. It still needs current authorization; expiry or revocation rejects the
retry without retiring the existing state. A different request needs the current
manifest/replay baseline. Rollback needs a fresh proposal over that baseline,
rollback intent, and matching external owner approval.

In-memory isolation assumes the consumer controls host code and callbacks.
Arbitrary code with the consumer's privileges can replace the consumer itself.
The persistent deployment below supplies the actual separate filesystem boundary.

## First persistent deployment profile

The governed overload of promoteMetamapGeneration takes a request and host
options containing mode "governed" and an absolute, externally fixed trustPath.
No output path, provider code or credentials are taken from the candidate. The
first profile requires Linux, root-owned trust/state storage, installed util-linux
flock, and a local filesystem
supporting kernel locks, same-filesystem atomic rename, and file/directory fsync.
Other operating systems fail closed. Network and unusual filesystems have no
acceptance evidence in this profile.

Install the promoter, interpreter, dependencies and service wrapper under the
consumer owner's root-controlled installation, outside agent-writable workspaces.
The privileged promoter writes that storage. The proposer must
run under a different unprivileged UID without access to the promoter UID, its
credentials, privileged command selection or ptrace of the promoter. The service
fixes code, argv, environment and trust location; only request data crosses the
boundary. The generic CLI alone does not configure that service boundary.

Provision the root-owned trust file and its ancestors without group/world write
permission. Provision the root-owned state directory with protected owner
permissions before promotion;
the library does not create it inside a proposal workspace. Paths are normalized,
absolute, disjoint from configured proposal roots and checked against resolved
roots. Trusted ancestors must be root-owned and protected; a sticky shared
ancestor such as /tmp is allowed for root-owned entries. Final trusted files must
be regular, non-symlink files without hard links. Immutable files must have no
write bits. The transaction lock is private to the promoter. Reads use no-follow
descriptors, file metadata checks and fatal UTF-8 decoding.

The accepted state layout is:

    state/
      .promotion.lock
      artifacts/<artifact-digest>/artifact-manifest.json
      artifacts/<artifact-digest>/<fixed-generated-files>
      manifests/<activation-digest>.json
      current.json

The promoter serializes writes with the Linux kernel lock. A fixed helper holds
the lock while reading its parent-owned pipe; promoter exit closes that pipe,
and helper exit releases the lock. There is no stale PID file to steal or remove.
Busy requests return a structured rejection and may be resubmitted with a current
baseline. The owner must serialize trust changes and other state administration
with this same deployment protocol. A privileged owner can bypass their own
service and is outside the unprivileged proposer threat model.

The promoter first reads complete current state under the lock and checks exact
approval. It writes candidate bytes into a private staging directory, syncs each
immutable file and directory, verifies actual file bytes/inventory, and publishes
the addressed artifact directory. It writes and syncs an immutable full activation
manifest. It then re-reads actual artifacts, current state and external trust,
rechecks current approval/time, and durably prepares one pointer. The final
approval check occurs after preparation; an atomic same-directory rename replaces
current.json, followed by a state-directory sync. No untrusted hook runs between
that authorization decision and publication.

The manifest binds the complete proposal, exact artifact inventory, accepted
approval, historical externally supplied trust configuration, expected previous
manifest, consumer/environment and trusted decision time. The recorded trust is
historical evidence; it cannot establish a new current trust root. Activation
time records the trusted authorization decision during preparation, not an
unobservable exact disk-persistence instant.

A failure before pointer replacement preserves current state. Unreferenced
staging/artifact/manifest files may remain after process death; they never become
current by discovery and are not automatically repaired or applied. A malformed
existing addressed directory fails closed. If pointer replacement succeeds but
directory sync or response handling fails, the result is indeterminate with
activated null and any verified current state that can be read. Inspect current
state before deciding whether to retry. This avoids treating a lost response as
a rejected deployment.

File/directory fsync requests depend on the operating system and storage device
honoring them. SIGKILL tests establish process-interruption behavior, not simulated
power-loss durability on every device.
[Node filesystem documentation](https://nodejs.org/docs/latest-v20.x/api/fs.html#filehandlesync),
[Linux rename semantics](https://man7.org/linux/man-pages/man2/rename.2.html),
[util-linux flock implementation](https://github.com/util-linux/util-linux/blob/master/sys-utils/flock.c).

## Consumer reads and revocation

readProtectedGovernedActivation takes the consumer's externally fixed trust path.
It reads one pointer once, checks that consumer/environment, validates the complete
addressed manifest and its historical approval, and verifies every exact immutable
file. The returned frozen state contains the files from that single generation.
It does not scan for or choose unreferenced candidate directories.

The first file ownership profile requires root-owned configuration, state and
descendants. It rejects files owned by the reading UID: a read-only consumer may
share the proposer UID, so that UID cannot become a filesystem trust root.
The independent consumer test reads root-owned state from an unprivileged UID
and rejects a proposer-owned pointer even with unchanged signed bytes.
Deployments with another service owner need a separately defined and tested
ownership profile.

Revocation prevents a new activation or retry. It does not silently retire an
already accepted generation: retirement is a separate consumer policy/action.
Changing the installed executor can also invalidate historical exact replay;
plan an explicitly approved migration rather than substituting runtime identity.

Generated TypeScript is part of the approved inventory. If a consumer compiles it
to JavaScript, its compiler/build output must also remain outside the proposal
workspace. The independent native test uses an owner-controlled compiler and
protected compiled output, then executes it under the unprivileged consumer UID.

## Wire command and fixed example

The CLI accepts strict UTF-8 JSON on stdin, capped at 64 MiB:

    metamap protected-promote /absolute/protected/trust.json < request.json
    metamap active /absolute/protected/trust.json

The request has no caller-clock, trust, hook or provider-path fields. The promoter
command accepts no evaluation-time override. Exit codes are 0 for activated or
already-active, 1 for rejection/error, 2 for usage, and 3 for indeterminate.
The active command reports active or empty; corrupt/incomplete state fails.

examples/activation/promoter.mjs is a fixed wrapper: it accepts no arguments,
uses the installed adjacent trust.json, reads the shared strict data stream,
and invokes the governed overload. Supply the protected configuration outside
source control during an owner-controlled installation. No production keys,
grants or installation are supplied by the example.

The root package, ./activation and ./activation-model expose the lifecycle API.
Three separate immutable schema identities define activation-request 1.0,
activation-manifest 1.0 and active-pointer 1.0. Published P09 and earlier records
retain their bytes.

## Acceptance evidence

Normal npm test includes portable memory/transport tests and Linux tests for the
actual transaction and permissions. The Linux suite requires a root test host or
passwordless sudo, installs a disposable root-owned package under a unique /tmp
directory, and runs the proposer/consumer as nobody (UID 65534). No production
configuration is touched. Synthetic private keys exist only in owner-controlled
temporary test storage and are removed with the fixture; they are never printed.

The suite attempts writes, chmod and deletion against trust, installed promoter,
SDK code, dependencies, active pointer and generated bindings. It also attempts
private-key reads, lock/state writes, legacy promotion and governed promotion
without the privileged host, and denies generic privileged command selection.
It separately checks writable proposals and readable,
native-executable protected outputs.

Concurrent requests, stale baselines, authorized retry, fresh owner rollback,
late expiry/revocation/output swaps, linked configuration and lost locks are
covered. Real promoter processes are killed at locked, artifacts-ready,
manifest-ready, before-commit and committed phases. Post-commit response failure
must report indeterminate. Trusted host phase hooks exist for observation/testing;
the wire protocol cannot select them.

The development Mac verifies the portable checks and reports Linux cases skipped.
M4 acceptance additionally requires the Linux suite to pass in CI; a local skip
does not establish the permission or transaction claims. BUILD_PLAN.md records
the exact completed gate and any remaining work.
